# ADR-0004：用 MQTT 遺言（LWT）偵測斷線，心跳逾時只當補網

狀態：已採納　日期：2026-09-09

## 背景

「即時監控各裝置連線狀況」是這個平台的核心功能之一。
最常見的實作是心跳逾時：記下每台裝置最後回報的時間，
背景工作定期掃描，超過 N 秒沒消息就標記離線。

## 決策

**主要手段用 MQTT 的 Last Will and Testament，心跳逾時降級為補網。**

裝置連線時向 broker 註冊一則遺言訊息（主題 `iot/status/{deviceId}`，內容 `OFFLINE`）。
連線異常中斷時，broker 會替它發出這則訊息。

## 為什麼心跳逾時不夠

**它分不清「裝置掛了」與「這段時間本來就沒有資料要回報」。**
事件驅動的裝置（例如門禁感測器）可能好幾分鐘沒有任何變化，
那是正常的。要靠心跳判斷，就得強迫所有裝置定期送空訊息，
等於為了偵測而增加流量——一萬台裝置每 30 秒一次心跳，就是額外的 333 則/秒。

**逾時門檻怎麼訂都是錯的。** 訂短了，網路抖動就誤報離線，值班的人很快學會忽略；
訂長了，真的斷線要等好幾分鐘才發現。而 LWT 是 broker 在 TCP 連線中斷的當下就送出，
沒有這個取捨。

**掃描成本隨裝置數線性成長。** 一萬台裝置每 10 秒掃一次，就是每 10 秒一次全表掃描。
可以用索引緩解（本專案的 `idx_device_last_seen` 就是為此建的），但它本質上是輪詢。

## 為什麼還是保留心跳逾時

LWT 有一個涵蓋不到的情況：**broker 自己重啟或崩潰**。
這時所有連線都斷了，但沒有任何 broker 來發送遺言。
心跳逾時是這個情況下唯一的偵測路徑。

因此 `Device.isSilentBeyond()` 仍然存在，但門檻設得寬鬆（分鐘級而非秒級），
定位是「補網」而不是主要偵測手段。

## 實作細節

**狀態訊息用 `retain = true`。** 平台重啟後一訂閱就能立刻拿到每台裝置的最後狀態，
不必等下一次狀態變化。沒有 retain 的話，平台重啟後所有裝置都會停在 UNKNOWN，
直到它們各自發生下一次狀態變化為止。

**正常關機的裝置自己先發 OFFLINE 再中止連線。**
對平台而言與 broker 代發的遺言沒有差別，都是同一則訊息。

**狀態轉移的合法性由 `DeviceStatus` 集中管理。**
`OFFLINE → DEGRADED` 是非法的：沒有連線就沒有「品質不佳的連線」可言。

## 代價

- **LWT 是 per-connection 的。** 模擬器若讓多台裝置共用一條 MQTT 連線以節省資源，
  就只能註冊一則遺言，失去逐台的斷線偵測。這是模擬器要面對的取捨，
  真實裝置各自持有連線，不受影響。
- **綁定 MQTT。** 若日後要支援 CoAP 或 HTTP 長輪詢的裝置，
  那些協定沒有等價機制，得回頭走心跳路徑。
- **broker 成為關鍵路徑。** broker 的可用性直接等於斷線偵測的可用性。
