# ADR-0006：裝置規則以「指標」為單位整個取代機型規則

狀態：已採納　日期：2026-09-09

## 背景

告警規則綁在機型上，一次套用到該機型的所有裝置。但總有例外：
放在冷藏區的溫濕度計，機型的「溫度 > 60 告警」對它沒意義，它要的是 75。
`alarm_rule.device_id` 欄位從 V1 就在，引擎卻只載入機型規則——
因為一旦兩種規則同時存在，就必須回答「衝突時聽誰的」。

## 決策

**裝置規則以指標為單位整個取代機型規則。**
某台裝置在 `temperature` 上有自己的規則，該機型所有 `temperature` 規則對它全部失效；
其他指標的機型規則照常套用。實作在 `AlarmRulePrecedence.resolve`，一個純函式，
引擎每筆讀數都經過它。

建立裝置規則的同時，引擎會解除該裝置上同指標機型規則的未解除告警並推播。
不做這件事，那則告警會永遠掛著：規則已不再被評估，沒有人會去解除它。

## 否決的方案

**兩邊都套用、取較嚴格者。** 冷藏區的溫濕度計想把門檻從 60 放寬到 75，
機型的 60 仍然會響，覆寫就沒有意義了。這個方案只能「收緊」不能「放寬」，
而放寬正是例外規則存在的主要原因。

**部分欄位覆寫。** 「只覆寫嚴重度但沿用門檻」這類需求聽起來合理，
但設定畫面要解釋「這條規則的門檻來自機型、嚴重度來自裝置、持續時間又來自機型」
——沒有人看得懂。整條取代的規則一句話就講完。

**一條規則同時綁機型與裝置。** 資料表的 `alarm_rule_scope` 約束擋掉這個可能，
理由同上：規則的適用範圍必須一句話說清楚。

## 後果

- 裝置規則的門檻檢查（是否落在量程內）用的是該裝置機型的指標定義，
  所以「裝置的機型」是建立時就要查的資料，API 回 400 帶原因。
- 停用一條裝置規則不會讓機型規則「回來」——快取載入時只看 `enabled`，
  停用的裝置規則不會進 `byDevice`，機型規則自然重新生效。這是刻意的，
  不需要另外定義「停用等於刪除」。
- 引擎的規則快取（30 秒）同時涵蓋兩種規則，寫入時整份失效。
