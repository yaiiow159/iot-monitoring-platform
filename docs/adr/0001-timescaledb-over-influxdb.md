# ADR-0001：時序儲存選用 TimescaleDB 而非 InfluxDB

狀態：已採納　日期：2026-09-09

## 背景

平台要同時放兩種資料：

- **設定資料**——機型、機櫃、裝置、告警規則。列數以萬計，關聯性強，需要外鍵與交易。
- **時序資料**——遙測讀數。每秒五萬筆，兩年跨度，幾乎只寫不改。

這兩種資料的存取模式差異極大，直覺會想用兩套儲存各自最佳化。

## 決策

**兩者都放進 TimescaleDB（PostgreSQL 擴充）。**

## 為什麼不用 InfluxDB ＋ PostgreSQL

這是最常見的組合，也是我前一份工作實際採用的方案。它有兩個代價，當時就吃過：

**第一，幾乎每個查詢都要跨兩邊。** 監控系統的查詢很少是純時序的，
真實的問題長這樣：

> 「列出配電櫃類型的機櫃裡，過去一小時平均功率超過額定值 80% 的裝置」

這需要 join 機櫃 → 裝置 → 機型（設定資料）與功率讀數（時序資料）。
兩套儲存的話這個 join 只能在應用層做：先查 Postgres 拿到裝置清單，
再拿著幾百個 id 去問 InfluxDB，最後在 JVM 裡合併。
等於把資料庫最擅長的工作搬到應用層重寫一遍，而且分頁與排序都要自己實作。

**第二，兩套查詢語言。** Flux 與 SQL 的心智模型不同，
團隊裡真正寫得動 Flux 的人通常只有一兩個，而告警規則與報表查詢會一直增加。

## TimescaleDB 換來什麼

- **一個 join 解決跨資料查詢**——上面那個問題就是一句 SQL。
- **連續聚合（continuous aggregate）在寫入時增量維護**，查詢時不必即時計算。
  這是「兩年跨度一秒內」的關鍵機制（見 [ADR-0002](0002-three-tier-downsampling.md)）。
- **欄式壓縮實測 10.4 倍**，每列 8.61 位元組（見 [performance.md](../performance.md)）。
  這個數字與 InfluxDB 的 TSM 引擎屬同一量級，沒有明顯落差。
- **一般 SQL**，既有的 JDBC、Flyway、連線池、監控工具全部沿用。

## 代價

- **寫入吞吐上限低於專用時序資料庫。** PostgreSQL 的 WAL 與 MVCC 是為了通用場景設計的，
  這部分開銷 InfluxDB 沒有。實測資料庫端約 12 萬筆/秒，對五萬點/秒的目標有 2.4 倍餘裕，
  但若目標提高到每秒五十萬點，這個決策要重新評估。
- **水平擴充比較麻煩。** TimescaleDB 的分散式版本（multi-node）已於 2.14 進入維護模式，
  單機撐不住時的路徑是垂直擴充或依租戶分庫，不像 InfluxDB 有現成的叢集方案。
- **必須自己管保留與壓縮政策**，InfluxDB 的 retention policy 概念比較直觀。

## 什麼情況下要推翻這個決策

- 寫入需求超過每秒二十萬點，且已確認瓶頸在 PostgreSQL 的寫入路徑而非應用層批次組裝
- 需要跨機房的時序資料複寫
- 設定資料與時序資料的查詢實際上從不交叉（那前提就變了，兩套儲存的代價消失）
