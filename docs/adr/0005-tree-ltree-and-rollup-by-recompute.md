# ADR-0005：監控樹用 ltree 存路徑，告警上浮用子樹重算而非計數器

狀態：已採納　日期：2026-09-09

## 背景

監控對象是一棵樹：Equipment 底下掛 Sensor，Sensor 可以無限自我嵌套，
Device 是葉節點。三個需求同時成立：

1. 任何 Sensor／Device 的告警，它的每一層祖先直到 Equipment 都要感知
2. 同層節點有明確順序，前端顯示不能是無序的
3. 一萬台裝置的樹，查詢要在一秒內

這是上一個專案實際踩過的坑，三個需求各自都出過問題。

## 決策一：路徑用 PostgreSQL 的 `ltree` 物化

節點存 `parent_id`（結構真相）與 `path`（例如 `1.4.9`，由祖先 id 串成）。

**為什麼不只用 `parent_id` 遞迴**：告警上浮要一路查到根，`WITH RECURSIVE`
每次都要跑一趟 CTE，深度越深越慢，而且「整個子樹的告警」要先展開子樹再 join。
`ltree` 搭配 GiST 索引，「子樹」是一個 `<@` 運算子的單次索引掃描，
「祖先」是路徑的所有前綴——甚至不用查資料庫，從路徑字串就能算出來。

**為什麼不用 closure table**：功能相同，但每個節點要存 O(深度) 列，
而且 ltree 是 Postgres 內建的，不用自己維護那張表的一致性。

**代價**：移動節點時要連同整個子樹的 `path` 一起改寫。本階段不開放移動，
只開放同層重排（改 `sort_order` 不動 `path`）。真要開放移動時，
子樹改寫是一句 `UPDATE ... SET path = new_prefix || subpath(path, nlevel(old_prefix))`，
不是難事，但要放在交易裡。

## 決策二：順序是後端的總序

每個節點有 `sort_order`，**所有回傳子節點的地方一律以 `(sort_order, id)` 排序**。
`id` 是決定性的平手判斷：兩個節點 `sort_order` 相同時，順序仍然唯一。

「前端顯示是無序的」這個問題，根源幾乎都不在前端。它來自後端只給了一個
可能相同的排序鍵，或根本沒排序就回傳，讓前端拿 Map／Set 承接後順序就散了。
把總序做在後端、契約明文禁止前端自行排序，問題就從源頭消失。

`sort_order` 之間留 1000 的間隔，插入中間取中點，用完約 10 次才需要重排一層。
不用小數（浮點精度會在多次二分後失效）也不用每次重新編號整層（一次插入變成 N 次寫入）。

## 決策三：上浮的值從子樹重算，不用遞增遞減的計數器

每個節點回傳的 `rollup`（子樹內最高嚴重度與告警數）**一定是從子樹重新算出來的**。

計數器版本（告警觸發時父節點 +1、解除時 −1）看起來省事，但它有一個經典的錯：
解除一則告警時父節點減一，但兄弟節點還在響，父節點的嚴重度卻已經被清掉——
「最高嚴重度」沒辦法靠減法維護，因為你不知道被解除的那則是不是唯一的 CRITICAL。
這個錯不會拋例外，只會在儀表板上安靜地顯示錯誤的顏色，
而且通常是在值班的人「看到綠燈所以沒去看」之後才被發現。

重算的成本：一次查詢，用 ltree 把整棵樹的未解除告警依祖先聚合：

```sql
SELECT ancestor.id, max(severity_rank), count(*)
FROM monitoring_node ancestor
JOIN monitoring_node descendant ON descendant.path <@ ancestor.path
JOIN alarm ON alarm.node_id = descendant.id AND alarm.state = 'FIRING'
GROUP BY ancestor.id
```

一萬個節點、數百則未解除告警，這個查詢在毫秒級。
即時推播時只需要重算「發生變化的那條祖先鏈」——從 ltree 路徑直接得到，
最多就是樹的深度那幾個節點。

領域層的 `MonitoringTree.build()` 是這個規則的純函式版本，
「解除一則後兄弟還在響、父節點不能變綠」有專門的測試守著。

## 被否決的方案

**Nested sets（左右值）**：讀取極快，但每次插入要改寫半棵樹的左右值，
對「設定中心會持續新增節點」的場景不划算。

**告警直接存在 Equipment 層**：等於放棄了「從哪裡冒上來」的資訊，
值班的人看到 Equipment 紅了還要自己往下找。上浮的意義正是保留來源路徑。
