# ADR-0003：MQTT 之後為什麼還要放一層 Kafka

狀態：已採納　日期：2026-09-09

## 背景

裝置已經透過 MQTT 連進來，broker 本身就有主題與訂閱。
直覺上消費端直接訂閱 MQTT 就好，多一層 Kafka 是多一個要維護的中介軟體。

## 決策

**MQTT 只負責裝置接入，之後立刻轉進 Kafka，所有下游從 Kafka 消費。**

## 理由

**三條下游路徑的失敗代價完全不同。**

| 消費端 | 掉一則的後果 | 積壓時該怎麼辦 |
|---|---|---|
| 寫入 TimescaleDB | 資料缺口，無法回補 | 慢慢追，絕不能跳過 |
| 告警引擎 | 可能漏掉事故 | 慢慢追，絕不能跳過 |
| WebSocket 推播 | 前端少更新一次 | **直接跳到最新，丟掉積壓** |

MQTT 的訂閱模型沒辦法讓這三者各自決定。用共享訂閱（shared subscription）勉強能做到
負載分攤，但做不到「推播端跳過積壓、入庫端從頭補」——因為 MQTT 沒有偏移量的概念，
訊息送出去就沒了。Kafka 的消費者群組各自持有偏移量，這件事才成立。

**尖峰時需要緩衝。** 一萬台裝置若因為網路恢復而同時重連並補送資料，
瞬間流量遠高於平均。Kafka 的磁碟佇列吸收這段尖峰，
讓入庫端以自己的節奏消化；沒有它的話，尖峰會直接打到 TimescaleDB 的寫入路徑。

**重放能力。** 告警規則改了想重新跑一遍過去一小時的資料、
入庫端有 bug 要重新處理——這些在 Kafka 是把偏移量往回調，在 MQTT 是做不到。

## 分區鍵一律用 deviceId

同一台裝置的訊息因此落在同一個分區，Kafka 保證分區內的順序。

沒有這個保證的話，「上線 → 離線」有機會被兩個消費端執行緒處理成「離線 → 上線」，
裝置狀態就永久卡在錯誤的值上——而且不會有任何錯誤訊息，
只會有一台在儀表板上顯示離線、實際上正常運作的裝置。

代價是熱點裝置會讓分區不均。目前每台裝置的流量相近，這不成問題；
若日後出現回報頻率差異極大的機型，要改用複合鍵。

## 代價

- **多一個要維運的中介軟體**，以及它的磁碟、分區規劃與監控。
- **端到端延遲增加**。實測待補，預期是個位數毫秒等級，對「即時監控」的需求可以接受。
- **橋接端（MQTT → Kafka）是新的單點**。目前靠無狀態設計與多副本緩解，
  但它掛掉時 MQTT 的訊息會直接流失——這是已知的缺口，
  要靠 broker 端的持久化訂閱補上，尚未實作。

## 被否決的方案

**消費端直接訂閱 MQTT。** 做不到差異化的積壓策略，也沒有重放。

**用 MQTT 共享訂閱做負載分攤。** 解決了水平擴充，沒解決偏移量與重放。

**不用 MQTT，裝置直接發 Kafka。** Kafka 的用戶端對嵌入式裝置太重，
而且沒有 LWT 這種協定層的斷線通知（見 [ADR-0004](0004-lwt-over-heartbeat-timeout.md)）。
