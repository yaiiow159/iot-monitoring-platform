# IoT 裝置監控平台

設定中心 ＋ 告警監控中心。承接一萬台裝置、每秒五萬個資料點的遙測，
保存兩年以上的歷史，並讓前端查詢維持在一秒內。

---

## 這個系統要解決什麼

監控平台的難處不在「把資料存下來」，而在**三個互相拉扯的需求同時成立**：

| 需求 | 單獨看很容易 | 湊在一起就衝突 |
|---|---|---|
| 每秒五萬點寫入 | 丟進佇列批次寫就好 | 但要即時告警，就不能等批次 |
| 兩年歷史 | 一直寫就好 | 但原始精度存兩年是 3.15 兆筆，單機放不下 |
| 查詢一秒內 | 加索引就好 | 但跨兩年的範圍掃描，再多索引也救不了 |

平台的設計就是在回答「這三件事怎麼同時成立」。

## 架構

```
                         ┌──────────────┐
   10,000 台模擬裝置 ───▶ │  MQTT Broker │ ── LWT 遺言訊息 ──▶ 斷線偵測
   （iot-simulator）      │    (EMQX)    │
                         └──────┬───────┘
                                │ 訂閱 telemetry/+/+
                         ┌──────▼───────┐
                         │ ingest-bridge│  驗證 ＋ 貼上機型定義
                         └──────┬───────┘
                                │
                         ┌──────▼───────┐
                         │    Kafka     │  扇出，讓三條路徑各自消費、各自失敗
                         └──┬────┬───┬──┘
              ┌─────────────┘    │   └─────────────┐
     ┌────────▼───────┐  ┌───────▼──────┐  ┌───────▼────────┐
     │ 寫入消費端      │  │ 告警引擎      │  │ 推播消費端      │
     │ 批次 COPY      │  │ 規則比對      │  │ WebSocket      │
     └────────┬───────┘  └───────┬──────┘  └───────┬────────┘
              │                  │                 │
     ┌────────▼──────────────────▼─────┐   ┌───────▼────────┐
     │         TimescaleDB             │   │    前端儀表板   │
     │  設定資料 ＋ 時序 hypertable      │   └────────────────┘
     │  ＋ 連續聚合（1 分／1 小時）      │
     └─────────────────────────────────┘
```

**為什麼 MQTT 之後還要 Kafka**——MQTT 負責的是「裝置怎麼連進來」，
它的訂閱模型不適合做重放與消費者群組。三條下游路徑的失敗代價完全不同：
推播掉一則沒關係，入庫掉一筆就是資料缺口，告警掉一則可能是事故。
用 Kafka 隔開之後，入庫可以慢慢追、推播可以直接丟棄積壓，
彼此不會互相拖累。詳見 [ADR-0003](docs/adr/0003-kafka-between-mqtt-and-consumers.md)。

## 兩年歷史怎麼放得下

原始精度不可能存兩年，這是算術問題不是調參問題：

```
50,000 點/秒 × 86,400 秒 × 730 天 = 3.15 兆筆
```

TimescaleDB 的欄式壓縮大約能壓到每筆 8 位元組，3.15 兆筆仍然是 **25 TB**。
所以平台採三層降採樣，每層各自負責一段時間跨度：

| 層 | 內容 | 保留 | 筆數 | 壓縮後 |
|---|---|---|---|---|
| 原始 | 每個資料點 | 7 天 | 302 億 | 約 240 GB |
| 1 分鐘連續聚合 | avg／min／max／count | 30 天 | 21.6 億 | 約 65 GB |
| 1 小時連續聚合 | avg／min／max／count | 5 年 | 8.76 億 | 約 26 GB |

合計約 330 GB，單機放得下。**「保存兩年」指的是小時級聚合**——
這一點在報告與 API 文件裡都寫明，不含糊帶過。
需要兩年前的原始精度是另一種需求，那要冷儲存與物件儲存，不在這個平台的範圍。

詳見 [ADR-0002](docs/adr/0002-three-tier-downsampling.md)。

## 查詢怎麼進一秒

關鍵不是索引，是**不要去掃原始資料**。查詢路由依「請求的時間跨度」決定讀哪一層：

| 跨度 | 讀取來源 | 最壞情況掃描量（單裝置單指標） |
|---|---|---|
| ≤ 6 小時 | 原始 hypertable | 21,600 筆 |
| ≤ 30 天 | 1 分鐘聚合 | 43,200 筆 |
| > 30 天 | 1 小時聚合 | 兩年 17,520 筆 |

跨兩年的查詢反而掃得比查六小時還少——因為它讀的是預先算好的小時桶。
連續聚合由 TimescaleDB 在寫入時增量維護，查詢時不需要即時計算。

跨裝置的聚合查詢（例如「全部機櫃過去兩年的溫度趨勢」）另有上限：
API 會限制回傳的序列數與時間桶數，超過就要求呼叫端縮小範圍或改用匯出。
**沒有上限的查詢遲早會有人打爆**，這比事後加快取實在。

## 模擬什麼

平台要能重現真實場域會遇到的狀況，否則告警規則沒有東西可以驗證：

- **機型（DeviceModel）**——不同機型回報不同指標組合與量程。
  溫度感測器只回溫濕度；電力模組回電壓、電流、功率因數；
  機櫃控制器回全部再加上門禁與風扇轉速。
- **機櫃（Cabinet）**——裝置裝在機櫃的槽位上。機櫃有類型（配電櫃／伺服器櫃／感測櫃），
  類型決定它容納哪些機型、以及整櫃層級的告警（例如整櫃功率超載）。
- **裝置狀態**——上線、離線、訊號不穩（間歇性斷線）、資料異常（超出量程）、
  時鐘飄移（時間戳落後）。
- **故障注入**——模擬器可指定比例的裝置進入異常模式，用來驗證告警規則與斷線偵測。

## 斷線怎麼偵測

用 MQTT 的 **Last Will and Testament**，而不是自己寫心跳逾時。

裝置連線時就向 broker 註冊一則遺言訊息；連線異常中斷時，broker 會替它發出這則訊息。
這是協定層級的保證，比應用層的「N 秒沒收到資料就當作離線」準確得多——
後者無法區分「裝置掛了」與「裝置這段時間本來就沒有資料要回報」。

心跳逾時仍然保留，但只作為 LWT 的補網（例如 broker 自己重啟的情況）。
詳見 [ADR-0004](docs/adr/0004-lwt-over-heartbeat-timeout.md)。

## 模組

```
iot-domain          領域模型與不變條件。零框架依賴。
iot-application     使用案例編排，只認得 Port 介面。
iot-infrastructure  TimescaleDB／Kafka／MQTT 的 Port 實作。
iot-api             REST 設定中心、歷史查詢、WebSocket 推播。
iot-simulator       裝置模擬器。獨立應用，只透過 MQTT 與平台溝通。
web                 前端儀表板。
```

依賴方向只能由外往內：`api → infrastructure → application → domain`。
由 `ArchitectureTest` 強制執行。

## 快速開始

```bash
docker compose up -d
```

```bash
mvn -q clean package -DskipTests
```

```bash
java -jar iot-api/target/iot-monitoring.jar
```

```bash
java -jar iot-simulator/target/iot-simulator.jar --simulator.device-count=1000
```

前端儀表板 http://localhost:3000，API 文件 http://localhost:8080/swagger-ui.html。
